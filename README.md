# PasarGuard Node — Railway / VPS Universal Deployment

This repository is a portable Docker wrapper around the official [PasarGuard Node](https://github.com/PasarGuard/node) image. It is **not the PasarGuard panel**. It runs one node that can be connected from any reachable PasarGuard panel, whether that panel is on Railway, a VPS, or another Docker host.

## What this version fixes

- Pins the upstream node image to `pasarguard/node:v0.5.4` instead of the moving `latest` tag.
- Works on Railway and ordinary Docker/VPS deployments.
- Uses `NODE_PUBLIC_HOST` for the TLS certificate SAN instead of assuming Railway private DNS.
- Uses Railway `PORT` only as a fallback; an explicit `SERVICE_PORT` always wins.
- Requires and validates a real UUID `API_KEY`.
- Persists the API key and generated certificate under `/var/lib/pg-node`.
- Regenerates only certificates generated by this wrapper when the public hostname changes.
- Saves connection details in `/var/lib/pg-node/connection-info.txt`.
- Keeps the official gRPC/TLS node API, so the panel does not need a custom client.

## Railway deployment

1. Create a new Railway project.
2. Deploy this GitHub repository as a service.
3. Attach a Railway Volume with mount path:

   ```text
   /var/lib/pg-node
   ```

4. Configure a public TCP endpoint/proxy to the service port. Set `SERVICE_PORT` to the internal port selected by the proxy. If Railway supplies a runtime `PORT` and `SERVICE_PORT` is not set, the entrypoint uses `PORT` automatically.
5. Set the following variables:

   ```text
   NODE_PUBLIC_HOST=<the public hostname used by the panel>
   SERVICE_PROTOCOL=grpc
   API_KEY=<a valid UUID, recommended>
   ```

   `NODE_PUBLIC_HOST` must be a bare hostname or IPv4 address, for example `node.example.com`; do not include `https://` or `:port`.
6. Deploy once and copy the complete certificate from the deployment log, or read it from `/var/lib/pg-node/connection-info.txt`.
7. In any PasarGuard panel, add a node using the displayed address, port, API key and complete PEM certificate.

### Important Railway networking rule

`RAILWAY_PRIVATE_DOMAIN` is reachable only by services in the same Railway project/environment. It is **not** a public address for a panel running on a VPS. For a panel outside Railway, use a public TCP endpoint and set `NODE_PUBLIC_HOST` to that public hostname.

## VPS / Docker deployment

```bash
docker volume create pasarguard-node-data

docker build -t pasarguard-node .
docker run -d \
  --name pasarguard-node \
  --restart unless-stopped \
  -p 62050:62050 \
  -v pasarguard-node-data:/var/lib/pg-node \
  -e NODE_PUBLIC_HOST=node.example.com \
  -e SERVICE_PORT=62050 \
  -e API_KEY=xxxxxxxx-xxxx-4xxx-8xxx-xxxxxxxxxxxx \
  pasarguard-node
```

For an IP address, use the IP in `NODE_PUBLIC_HOST`; the generated certificate receives an IP SAN. For a domain, point DNS to the VPS first and use the domain in the variable.

## Panel connection values

Use these values in the node form of the panel:

| Field | Value |
|---|---|
| Address | The exact `NODE_PUBLIC_HOST` printed by the node |
| Port | `SERVICE_PORT` printed by the node |
| Protocol | gRPC for the standard official node client |
| API key | The UUID printed once or supplied through `API_KEY` |
| Certificate | The complete PEM certificate, including `BEGIN CERTIFICATE` and `END CERTIFICATE` |

The panel must be able to route to the address and port. The TLS certificate hostname must match the address entered in the panel.

## Environment variables

See [.env.example](.env.example) for all supported variables. The upstream image also supports the official `PG_NODE_WG_*` variables.

## Security notes

- Prefer setting `API_KEY` explicitly in Railway/VPS secrets.
- Do not publish the certificate and API key together in a public issue or chat.
- Keep `/var/lib/pg-node` persistent; otherwise the generated key/certificate can change after redeploy.
- The API key is intentionally printed only when a new key/certificate is created. Use `FORCE_PRINT_CONNECTION_INFO=true` for a controlled reprint.
- WireGuard host routing may require Linux kernel capabilities unavailable on some managed platforms. The node API can be reachable even when WireGuard data-plane features are not supported.

## Upgrade the upstream node

The image is pinned for reproducibility. To upgrade, change the `PASARGUARD_NODE_IMAGE` build argument in the Dockerfile to an existing upstream version, test panel compatibility, and redeploy. Do not silently switch back to `latest` in production.
